## 0. 前提

| 项 | 结论 |
|---|---|
| 项目形态 | 完全开源至 GitHub |
| **License** | **MIT**（本体），第三方 provider 各自原许可 |
| 对外出口 | 单一 OpenAI 兼容端点 |

| 底座选型 | 路线 B：`new-api` 承担渠道路由 / 模型别名 / 计费统计 |
| 不回退项 | `--no-sandbox`、CRLF+GBK 批处理、单 `.rsrc` 段、DPI 换算 |

**一条决定全局形态的硬约束**：所有反向 2api 项目（含 `new-api`）都是**独立 HTTP 服务**，不是可 import 的库。因此 provider 层的唯一正确形态是 **「子进程托管 + HTTP 转发」**，Mergence 自身不承载路由逻辑。

### License 策略（已定：MIT）

Mergence 本体采用 **MIT**。之所以成立，是因为架构上刻意做了两件事：

1. **不 import 任何 AGPL 代码**——`new-api` 只以独立进程运行，不构成衍生作品。
2. **不随包分发第三方二进制**——规避 AGPL「提供对应源码」的分发义务。

`README` 需逐项列出第三方 provider 的来源与许可，并声明「本项目不分发其二进制，由用户自行获取」。

## 1. 面板归属：自研统一总面板

### 决定
**自研一个统一总面板，从现有 WorkBuddy 面板演进而来；不内嵌 new-api 自带面板。**

### 理由
1. **信息割裂**：new-api 面板只能看到它自己的渠道/额度，看不到 WorkBuddy 的账号池、定时任务、积分构成、会话粘性——恰好是现有面板最有价值的部分。
2. **双面板 = 双份认知负担 + 两套鉴权 + 两套主题**，与「单一应用」的目标冲突。
3. **演进成本最低**：现有面板已具备完整设计令牌体系（明暗主题、严格 CSP、环形日志缓冲、`go:embed` 零外部构建），扩展比重写便宜得多。

### 与 new-api 的职责边界
```
Mergence 总面板 ──Admin API──▶ new-api（无头运行，自带面板关闭）
      │                              │
      │                              ├─ 渠道路由 / 权重 / 故障转移
      └── 直连各 provider 管理接口 ───┴─ 模型别名 / 用量计费
```
- 面板只认 **Mergence 自己的鉴权**，用户永远只登录一次。
- new-api 的 Web 面板在配置里关闭，避免暴露第二个入口。

### 总面板信息架构（5 个一级页签）

| 页签 | 内容 |
|---|---|
| **总览** | 全局健康灯、今日调用量/成本、渠道状态、异常 TOP、额度告警横幅 |
| **额度** | 合集式额度视图（第 2 节） |
| **渠道** | provider 增删、凭证录入、启停、权重、健康检查、进程状态（第 3 节） |
| **日志** | 结构化请求流水（第 7 节） |
| **设置** | 端口、路由策略、鉴权、数据目录、日志级别 |

## 2. 额度页：合集式双列表

### 设计动机

WorkBuddy 是**按模型计费**的（每个模型有独立倍率、tier、可用性），而现有面板只到**账号级**——显示「积分 1112/1119」，**看不出"哪个模型我还能跑多少"**。接入多渠道后问题放大：用户真正要回答的是「现在还能用哪个模型」，而不是「我总共还有多少分」。

### 呈现形式：折叠合集

默认**收起**，只显示一行摘要（总渠道数、可用模型数、告警数），**点击后才展开**内部模型列表：

```
┌─ ▸ 额度合集    3 个渠道 · 14 个模型 · 2 条告警 ─────────────────┐
└──────────────────────────────────────────────────────────────┘
                        │ 点击展开
                        ▼
┌─ ▾ 额度合集    [ 按渠道 ] [ 按模型 ]        🔍 搜索   ⚙ 筛选 ────┐
│                                                                  │
│   （展开后是两个列表视图，见下）                                    │
│                                                                  │
└──────────────────────────────────────────────────────────────┘
```

**为什么默认收起**：解锁后的账号 + 多渠道 × 多模型会产生几十行，直接铺开会淹没「总览」。收起态给摘要，展开才给细节——符合「一屏看结论，点击看明细」的原则。

### 列表一：按渠道分类组织

按 provider 分组，每组展开看该渠道下的模型与账号。

```
▼ WorkBuddy                                    可用 · 8 个模型
    模型              可用额度    覆盖账号    状态
    GLM-5.3              820       2/3       正常
    GLM-5.3-Flash       1540       3/3       正常
    DeepSeek-V4           89       1/3       ⚠ 额度偏低
    …（可切换「按账号」透视）

▼ ZCode                                        可用 · 4 个模型
    GLM-5.3              无限      1/1       T1
    GLM-5.3-Flash        2400      1/1       T2

▼ Trae                                         降级 · 1 个模型
    auto                 冷却中     0/1       ⚠ 上游 429
```

**这层回答**：每个渠道有哪些模型、各自还剩多少、有没有异常。

### 列表二：按厂商归类

**以模型为中心**的视图：先按**厂商**分组，组内列该厂商的模型，每个模型汇总**它在所有渠道上的可用量**。

```
▼ 智谱 GLM
    GLM-5.3        总可用 820    ← WorkBuddy(820) · ZCode(无限)
    GLM-5.3-Flash  总可用 3940   ← WorkBuddy(1540) · ZCode(2400)

▼ DeepSeek
    DeepSeek-V4    总可用 89     ← WorkBuddy(89)
    DeepSeek-V4-Pro 总可用 无限  ← Trae(无限)

▼ Anthropic
    Claude Sonnet  总可用 无限   ← ZCode 别名映射 · Trae 别名映射

▼ OpenAI
    GPT-4o         总可用 无限   ← Trae 别名映射
```

**这层回答**：同一个模型能从哪里拿到、合计还有多少——**跨渠道自动汇总，这正是聚合网关的核心价值**。

点任一模型 → 右侧抽屉展示该模型在各渠道/账号的**逐条明细**与近期调用统计。

### 数据来源

- provider 已有 `ModelRate` 倍率表 + 各账号 billing 快照，**数据齐全，缺的只是聚合视图**
- 新增 `GET /panel/api/quota_matrix?view=channel|vendor&expand=<key>`，返回分组结构
- 折叠状态、当前视图、透视方式记入面板本地存储，刷新后保持

### 顺带覆盖「所有 WorkBuddy」

矩阵天然支持多个 WorkBuddy 账号组（CN 区 / 海外区 / 不同套餐），账号维度加分组列即可，无需另建面板。

## 3. 自定义渠道模块

> 这是第三个内容模块：**用途、结构、呈现方式**逐项定义。

### 用途

把**任意 OpenAI 兼容端点**接入 Mergence，**无需为每个小众 provider 写适配器**。解决三类现实需求：

1. **官方 API 直连**：智谱 BigModel、DeepSeek、SiliconFlow、Moonshot 等本来就提供 OpenAI 兼容端点，没有理由再包一层 2api 项目。
2. **自建/私有部署**：本地 `vLLM` / `Ollama` / LM Studio、公司内部网关。
3. **长尾与新项目**：未来新出现的 2api 项目、小众中转站——不必等 Mergence 发版适配。

**同时它是 OpenRouter 的归宿**：OpenRouter 本身就是 OpenAI 兼容端点，不需要专门的代码路径，只需一个**预设模板**。

### 结构（配置字段）

分三段，只有第一段是必填：

**基础（必填）**
| 字段 | 说明 |
|---|---|
| 显示名称 | 面板与日志里的标识 |
| Base URL | 如 `https://openrouter.ai/api/v1` |
| API Key | **支持填多个**，自动构成小账号池并轮询 |
| 协议 | `OpenAI Chat Completions` / `OpenAI Responses` / `Anthropic Messages` |
| 模型前缀 | 汇聚出口的 model 名前缀，如 `or/`；留空则用名称自动生成 |

**模型**
| 字段 | 说明 |
|---|---|
| 获取方式 | **自动**（拉 `/v1/models`，可多选）/ **手动**（逐条填写） |
| 模型列表 | 支持别名映射（把上游名映射成自定义名） |
| 上下文 / 最大输出 | 可选，用于面板展示与请求裁剪 |

**高级（可选）**
| 字段 | 说明 |
|---|---|
| 权重 / 优先级 | 参与聚合路由 |
| 自定义请求头 | 很多中转站靠特定 header 鉴权或标识来源 |
| 超时 / 重试 | 覆盖全局默认 |
| 健康检查路径 | 默认 `/v1/models` |
| 代理 | HTTP/SOCKS5 |

### 呈现方式

1. **入口**：「渠道」页 →「添加渠道」→ 选择类型，第一项就是 **「自定义 OpenAI 兼容端点」**；下方并列 **预设模板**：`OpenRouter`、`智谱 BigModel`、`DeepSeek`、`SiliconFlow`、`Moonshot`——选中模板后**预填 Base URL 与协议，只需补 Key**。

2. **表单**：三段式折叠（基础默认展开，模型/高级按需展开），与总面板既有表单语言一致。

3. **保存前必须「测试连接」**：
   - 拉一次 `/v1/models` → 展示识别到的模型数
   - 试跑一次最小 `chat` 请求（`max_tokens=1`）→ 展示首字节耗时
   - 任一步失败**阻止保存**并高亮出错字段（避免"加了个永远 401 的渠道"）

4. **接入后**：与内置渠道**完全同权**——出现在额度合集（第 2 节）、日志、告警里，无需特殊分支。

### 与其它 provider 的关系

引入自定义渠道后，provider 收敛为**两类**，实现上互不干扰：

| 类别 | 运行方式 | 成员 |
|---|---|---|
| **内嵌型** | Mergence 进程内直接实现 OpenAI 兼容端点 | `WorkBuddy`（搬迁进来）、`自定义渠道` |
| **托管型** | 独立子进程，编排器负责拉起/健康检查/日志归一 | `new-api`、`zcode2api`、`trae-local-api` |

**OpenRouter 不再是独立成员**，而是内嵌型的一个预设模板。

### 实现状态（P3 已落地）

| 能力 | 状态 | 说明 |
|---|---|---|
| 渠道增删改查 + 面板表单 | ✅ | `/api/channels`；三段式折叠表单、预设模板、启停开关 |
| 保存前测试连接 | ✅ | 拉模型列表 + 跑一次 `max_tokens=1` 真实对话；失败**归因到具体字段**并高亮 |
| 多 Key 轮询池 | ✅ | 轮询取用；`401/403` 冷却 10min、`429` 60s、网络/5xx 5s；失败次数越多冷却越久（上限 8×）。**不做永久拉黑** |
| 模型列表聚合 | ✅ | `/v1/models` 汇总所有启用渠道，带前缀 |
| `Chat Completions` 协议 | ✅ | **保真直通**（只改 `model` 字段），流式 SSE 一个字节都不碰 |
| `Anthropic Messages` 协议 | ✅ | 双向转换（含 tool_use/tool_result、图片、system 提取、连续同角色合并）；流式逐事件转成 OpenAI SSE |
| `Responses` 协议 | ⏳ **P4 后补齐** | 配置里保留该选项，但调用时返回 **501 + 明确说明**。刻意不「回落成 chat 再试」——那样只会让用户收到上游的谜之 400 |
| `auto` 路由 | ⏳ **P6/P7 后** | 需要额度与健康度数据；当前返回 400 并提示改用带前缀的具体模型名 |

**路由规则**（前缀在配置层保证唯一，`normalize` 会禁用重复者，所以不会歧义）：

1. **前缀匹配**：`or/openai/gpt-4o` → 命中前缀 `or/` 的渠道，上游模型名 `openai/gpt-4o`
2. **前缀匹配但未在声明列表里** → **原样透传**。上游随时上新模型，不该逼用户先改配置
3. **裸名匹配**：不带前缀、但与某渠道声明的「对外名或上游 ID」完全相同；多渠道路由同一模型时按 `Priority` 降序 → `Weight` 降序 → 配置顺序择一
4. 别名映射：`{"id":"glm-4.6","alias":"glm"}` → 对外 `zhipu/glm`，上游发 `glm-4.6`

**两个刻意做强的细节**：

- **Key 沿用语义**：编辑渠道时 Key 框留空 = 沿用已保存的 Key。实现上靠「JSON 字段缺失（`nil`）vs 空数组」区分「没改」与「清空」，比在 UI 上回显掩码再猜用户动了没有可靠得多。测试连接遵守同一语义，否则「编辑时点测试」会因为 Key 为空而误判失败。
- **上游错误原样透传**：上游返回 4xx/5xx 时，把它的**状态码与错误体原样交给客户端**，而不是包装成「网关内部错误」。判断依据是：客户端需要能区分「我的请求有问题」与「网关拿到请求但上游不行」，这直接决定它的重试策略。

## 4. 托盘与窗口生命周期

### 决定
**关闭主窗口 ≠ 退出。** 关窗只隐藏窗口并驻留系统托盘（任务栏右下角通知区域）；**只有托盘右键菜单的「退出」才真正结束进程并释放全部资源。**

### 状态机
```
        ┌──────────────┐   关窗 (X)   ┌──────────────┐
        │  窗口可见     │ ───────────▶ │  托盘驻留     │
        │  (Running)    │ ◀─────────── │  (Hidden)    │
        └──────┬───────┘  双击托盘 /   └──────┬───────┘
               │          「显示主窗口」        │
               │                              │ 菜单「退出」
               │                              ▼
               └─────────────────────▶ ┌──────────────┐
                                       │  Quitting    │ ──▶ 有序释放 ──▶ 进程结束
                                       └──────────────┘
```

### 关键技术点（含踩坑预判）

**(1) 拦截 WM_CLOSE —— 必须窗口子类化**

go-webview2 的窗口过程收到 `WM_CLOSE` 时**直接 `DestroyWindow`**，不接受外部干预。因此需在窗口创建后用
`SetWindowLongPtrW(hwnd, GWLP_WNDPROC, ourProc)` **子类化**：我们的过程拦截 `WM_CLOSE`（改为隐藏 + 首次弹气泡），其余消息经 `CallWindowProcW` 转发给原过程。

> 前提：`w.Window()` 能拿到 HWND（go-webview2 已暴露），**无需修改上游**。

**(2) 托盘消息循环 —— 独立线程，不与 WebView2 冲突**

托盘需要一个窗口接收 `Shell_NotifyIcon` 的回调（`WM_APP+1`），**不能复用 WebView2 的窗口**。
做法：**单独起一个线程**创建 **message-only window**（`HWND_MESSAGE`）+ 自己的 `GetMessage` 循环。Windows 允许每线程独立消息循环。菜单点击后用 **`w.Dispatch(func())`** 把动作投递回 UI 线程执行——这是 go-webview2 提供的正规跨线程入口。

**依赖选择：直接用 Win32（`Shell_NotifyIconW`）**
- 理由：主程序已有 Win32 syscall 层；零新增依赖；完全掌控消息循环
- 备选：`getlantern/systray`、`fyne.io/systray`——但它们是「主循环归托盘所有」的设计，与 WebView2 循环并存要额外绕行，收益不大

**(3) 托盘图标来源 —— 从内嵌 PE 资源加载**

**不要依赖 `app.ico` 文件存在**（用户可能只拷走 exe）。用 `LoadIconW(GetModuleHandle(nil), MAKEINTRESOURCE(1))` 直接从 exe 的图标资源组加载——该资源由 `go-winres` 在**构建期写入 PE 的 `RT_GROUP_ICON`**，与 DPI 清单、版本信息同处于**单个 `.rsrc` 段**（已验证不冲突）。托盘取 `SM_CXSMICON`（通常 16×16），Windows 会从图标组自动挑选最佳尺寸。

**(4) ⚠️ Explorer 重启后图标消失 —— 必须处理**

`explorer.exe` 崩溃或重启会清空通知区域，所有托盘图标消失且**不会自动恢复**。标准做法：监听 `RegisterWindowMessageW("TaskbarCreated")`，收到后重新 `Shell_NotifyIconW(NIM_ADD)`。
**不做这一步的托盘实现都是不完整的**，用户会遇到「图标莫名其妙没了」。

**(5) 退出时序（严格有序，漏一步就留残留）**

| # | 动作 | 为什么必须在这一步 |
|---|---|---|
| 1 | 置 `quitting = true` | 否则后续 `WM_CLOSE` 又被拦成「隐藏」，**永远退不出去** |
| 2 | **`Shell_NotifyIconW(NIM_DELETE)`** | **必须最早**——崩溃或卡住时不在通知区留「幽灵图标」 |
| 3 | 真正关闭窗口（`DestroyWindow`） | 走正常销毁路径 |
| 4 | 等待 webview `Run()` 返回 → `w.Destroy()` | 释放 WebView2 环境与用户数据目录句柄 |
| 5 | 编排器 `Shutdown(ctx, 8s)`：向每个托管 provider 子进程发终止 → 等待 → 超时 `TerminateProcess` | 先礼后兵，不留孤儿进程占端口 |
| 6 | WorkBuddy provider `pool.Flush()` | 主动落盘一次（虽然每 5s 已自动落盘，退出时补一次） |
| 7 | 关闭日志文件、释放端口记录锁 | — |
| 8 | `PostQuitMessage(0)` 结束托盘线程 | **漏这步进程不结束**——托盘线程还活着 |

**(6) 单实例（顺带解决一个体验问题）**

用命名互斥体 `CreateMutexW("Global\\Mergence.SingleInstance")` 保证单实例；第二次启动**不再开新进程**，而是找到已有窗口并**唤出**它（`ShowWindow(SW_RESTORE)` + `SetForegroundWindow`）。

> 现实中用户会反复双击快捷方式；没有单实例会出现多个进程抢同一批端口、状态互相覆盖。

|---|---|
| 左键单击 / 双击 | 唤出主窗口 |
| 右键 | 弹出菜单 |

## 5. 分发形态（已定）

### 决定：单文件主程序 + 第三方 provider 按需拉取

**GitHub Releases 产物**

| 产物 | 说明 |
|---|---|
| `Mergence.exe` | Windows x64 **单文件**（壳 + 总面板 + 全部内嵌型 provider），约 7–10 MB |
| `checksums.txt` | 各产物 SHA256 |
| 源码包 | GitHub 自动提供 |

**托管型 provider 不进包**：由用户在「渠道」页点「添加」时按需获取，落到
`<数据根>\data\providers\<name>\<version>\`

> `<数据根>` 默认就是 exe 所在目录（便携形态），不可写时回落到 `%LOCALAPPDATA%\Mergence`。
> 见 README「运行与配置」。

下载前**必须展示来源 URL 与 SHA256**，并允许改为手动指定本地路径。

### 三个理由

1. **License 干净**（最关键）：不打包 AGPL 二进制 → 不触发「提供对应源码」义务 → 本体可保持 MIT。
2. **体积与版本自由度**：单文件 ~10 MB vs 打包全部后的 100 MB+；`new-api` 仍在发 rc，按需拉取不会把版本钉死。
3. **可换可替**：托管型 provider 都是独立进程，用户可换成自己的 fork 而不动 Mergence。

> ⚠️ **风险提示**：「一键下载」在部分司法辖区可能被视为协助分发。做法上把下载做成**用户显式主动触发**（展示来源与校验值），而非静默预装；并保留「仅手动指定本地路径」开关。

## 6. 端口策略：动态分配

### 决定：Mergence 统一分配 + 持久化复用 + 面板明示

**为什么不用纯 OS 自动分配**：托管型 provider 基本不接受 `:0`，且用户需要知道端口才能填客户端 base_url。所以是「编排器选端口 → 传给子进程 → 面板显示」。**内嵌型 provider 无此问题，直接用 `:0`。**

### 五步流程

1. **分配** —— 启动托管 provider 前，用 `net.Listen("tcp","127.0.0.1:0")` 探空闲端口后立即释放。
2. **传递** —— 双通道下发，兼容不同 provider 的配置习惯：
   - 我们的约定：`MERGENCE_PORT=<port>`
   - provider 原生变量：如 `new-api` / `trae-local-api` 的 `PORT`
   - 不支持改端口的（如 `glm-zcode-2api` **硬编码 7864**）→ 走降级模式：**固定端口 + 冲突预检**，冲突则明确报错而非静默失败。
3. **确认** —— 轮询 `127.0.0.1:<port>/healthz` 直到就绪或超时。
4. **冲突处理** —— 端口被抢 → 换端口重试（最多 3 次）→ 仍失败则该渠道标记「启动失败」并在总览页高亮。
5. **持久化** —— `ports.json` 记录上次端口，**重启优先复用**（用户书签、外部客户端不会每次失效）；不可用再重新分配。

### 每实例独立数据目录
```
<数据根>\data\instances\<渠道名>\data\
```
避免多实例互踩数据库 / 状态文件。

### 对外入口
new-api 的对外端口同样动态分配，但**总面板顶部常驻显示当前 base_url 与 API Key，支持一键复制**——把"端口会变"对用户的影响降到零。

## 7. 日志可读性优化

### 现状诊断（实测样本）

```
2026-10-02 01:18:01 === 桌面壳启动，服务目录 <项目根>\\workbuddy2api-panel ===
2026-10-02 01:18:02 已启动服务进程 pid=13932
2026-10-02 01:18:05 窗口物理尺寸 2400x1480（逻辑 1200x760，显示器 DPI=192，缩放 200%）
```

| # | 问题 | 后果 |
|---|---|---|
| 1 | **无结构**：纯自由文本 | 无法按账号/模型/状态筛选 |
| 2 | **无级别**：噪音与错误混排 | 重要信息被淹没 |
| 3 | **多渠道后必串**：4 路日志汇流 | 分不清哪行来自谁 |
| 4 | **无请求链路**：一次调用跨 4 个进程 | 排查要手工拼时间戳 |
| 5 | **面板只能看原始行** | 会滚动、无检索、无下钻 |

### 改法

#### (1) 结构化日志，双通道输出
用 Go 标准库 `log/slog`（无第三方依赖）：
- **文件**：JSON Lines → 可 `jq`、可 grep、可导入分析
- **内存环形缓冲**：保留**结构化对象**（非字符串），供面板直接消费

所有 provider **强制对齐同一套字段**：
```json
{"ts":"2026-10-02T01:18:02.123+08:00","level":"INFO","component":"orchestrator",
 "event":"provider.ready","provider":"workbuddy","port":51823,"pid":13932,"dur_ms":820}
```

#### (2) 全链路请求 ID
一次下游调用生成一个 `req_id`，透传到 `new-api → provider → 上游`，**每一跳的日志都必须带上它**。「为什么这个请求 500」不再是考古，而是按 id 一搜到底。

#### (3) 面板日志页：从「文本流」改成「表格 + 详情抽屉」

| 时间 | 级别 | 渠道 | 账号 | 模型 | 状态 | 耗时 | 概要 |
|---|---|---|---|---|---|---|---|
| 01:18:02 | INFO | workbuddy | 林渊… | glm-5.3 | 200 | 1.2s | 完成 |
| 01:18:03 | WARN | zcode | — | GLM-5.3 | 429 | 0.3s | 账号耗尽，已切换 |
| 01:18:04 | ERROR | trae | — | auto | 502 | — | 上游连接被拒 |

- 顶部筛选：级别（**默认隐藏 DEBUG**）、渠道、模型、状态码、时间范围
- 关键字搜索 + 「只看错误」一键切换
- 点击任意行 → 右侧抽屉：完整 JSON + **同一 `req_id` 的所有关联事件（链路视图）**
- 支持导出当前筛选结果为 JSONL

#### (4) 降噪与分级
| 事件 | 级别 | 理由 |
|---|---|---|
| 心跳 / 健康检查 / 定时轮询 | `DEBUG` | 高频噪音，默认不显示 |
| 上游重试、账号切换、冷却 | `WARN` | 用户**应该**知道但不致命 |
| 额度耗尽、渠道全挂、鉴权失效 | `ERROR` | 总览页顶部弹告警横幅 |

日志级别做成**设置项**，无需改代码或重启。

#### (5) 子进程日志归一
托管型 provider 的 stdout/stderr 由编排器捕获，**按行打上 `provider=<name>` 标签**后并入同一日志流；非 JSON 的原生行包成：
```json
{"level":"INFO","provider":"new-api","raw":"[GIN] 2026/10/02 - 200 | 1.2ms | 127.0.0.1 | GET /api/status"}
```
保证面板里**永远不出现「不知道哪来的」裸行**。

### 用户感知到的变化
> 从「看着会滚动的一整屏中文文本找线索」
> → 「按渠道/模型/状态筛一下，点开看完整链路」

排查「为什么这个模型 429」从「翻 500 行日志」变成 **3 次点击**。

## 8. 额度轮询与自动 ban

### 目标
固定间隔自动查询各 provider × 各模型的剩余额度；**把额度已耗尽的模型自动 ban 掉**，不再参与路由；额度恢复后自动解 ban。

### 关键判断：ban 的粒度必须是「账号 × 模型」

现有 `pool` 的冷却 / 熔断 / 降权都是**账号级**的。但一个账号的 `GLM-5.3` 额度耗尽，**不代表**它的 `GLM-5.3-Flash` 也不能用——WorkBuddy 是按模型计费的。

所以自动 ban 必须落在 **`账号 × 模型` 二维单元格**上，而不是整个账号。这是本模块与现有机制最大的区别，也是必须新增的数据结构：

```
availability[account][model] = {
    state:      可用 | 耗尽 | 冷却 | 未知 | 手动禁用
    until:      <恢复时间，可为空>
    reason:     主动查询 | 上游 402 | 上游 429 | 手工
    checked_at: <最近确认时间>
}
```

### 探测方式：被动优先，主动兜底

| 方式 | 成本 | 优先级 |
|---|---|---|
| **被动**：从请求响应里读余额/额度字段 | 零额外成本 | **优先** |
| **被动**：上游返回 402 或 quota 类错误 → 立即标记该单元格耗尽 | 零额外成本 | **优先** |
| **主动**：定时调用 provider 的额度查询接口 | 需配额与限流，但能发现「还没用过就已经没额度」的模型 | 兜底 |

**为什么被动优先**：主动查询要打上游，频率高了可能被限流；而请求响应里往往已带余额（WorkBuddy 的 billing 字段就是这么来的）。

### 定时任务

- 间隔可配置，**默认 10 分钟**（WorkBuddy 已有的余额后台刷新默认 5 分钟，本模块复用它，只把结果**扩展到模型粒度**）
- **错峰**：多个 provider 的查询分散在间隔窗口内，不集中打
- **⚠️ 失败不退避到误 ban**：连续 N 次查询失败 → 标记为 `未知` 而**不是** `耗尽`。这条是鲁棒性关键——否则查询接口自己挂了会把所有模型误 ban，服务直接不可用
- 只在结果缓存临近过期时才真正发起查询，避免无意义请求

### ban 的执行点

在**路由选号**阶段过滤：`Pick(model)` 时跳过 `state != 可用` 的单元格。

若某模型的所有单元格都不可用 → 该模型标记「全局不可用」，请求**直接返回明确错误**（列出各来源的原因与最早恢复时间），**而不是打到上游再失败**——省一次无效往返，且错误信息对用户有用得多。

### 解 ban 策略

1. **有明确恢复时间**（如「次日 04:00」）→ 注册定时器，到点自动解除并标记「待验证」
2. **无明确时间** → 下一个轮询周期主动查询确认后解除
3. **恢复后先「试探」**：不立刻全量放行，先放 1 个账号跑小流量验证，成功再全面恢复——避免「刚恢复又耗尽」的抖动

### 与面板的联动
- 额度合集（§2）的两个列表**直接消费这张矩阵**
- 新出现「全局不可用」的模型 → 总览页告警横幅（ERROR 级）
- 提供「手动解 ban / 手动 ban」入口与 ban 历史记录

### 配置项
| 项 | 默认 | 说明 |
|---|---|---|
| `quota_poll_interval` | `10m` | 轮询间隔 |
| `auto_ban_enabled` | `true` | 是否启用自动 ban |
| `ban_failure_threshold` | `3` | 连续查询失败几次后转「未知」而非「耗尽」 |
| `probe_on_recover` | `true` | 恢复时是否先小流量试探 |

实测确认（读取本机 `~/.dsh/` 得到，非推测）：

- **插件框架 = Cordis**（Node.js 依赖注入框架）。插件是 **npm 包**，安装在 `~/.dsh/profiles/desktop/`，由 `cordis.patch.yml` 逐项启用与配置。

- **provider 机制**：`@deepseek-ai/dsh-llm-*` 系列，形如 `dsh-llm-deepseek-account`、`dsh-llm-deepseek-api-key`，在配置里声明 `models` 列表。
- **已有额度基础设施**：`~/.dsh/dsh-usage/provider-snapshots.json`（provider 额度快照）+ `~/.dsh/storages/cost-meter/ledger.json`（成本账本）。

> 注意：`provider-snapshots.json` 里这些 provider 的 `credential` 均为 `none`，即**未配凭证所以取不到额度数值**——这正是插件要补的位置。

### 插件形态：一个 Cordis 插件包 `dsh-mergence`

包含两部分能力：

**① provider 注册** —— 把 Mergence 注册为 dsh 的 LLM provider
- `base_url`：Mergence 的动态端口（插件启动时读 Mergence 的 `ports.json`，或调用其本地发现接口）
- 模型列表：`GET /v1/models` 拉取，带 `provider/` 前缀
- 效果：**dsh 里可直接把 Mergence 的任意模型设为对话模型**——一次配置用到所有渠道

**② 额度组件** —— 显示 Mergence 上各家模型的剩余额度

### 数据来源：Mergence 新增一个插件端点

```
GET /api/quota
{
  "updated_at": "2026-10-02T01:40:00+08:00",
  "vendors": [
    { "vendor": "智谱 GLM",
      "models": [
        { "id":"glm-5.3", "display":"GLM-5.3",
          "free": false, "remaining": 820, "total": 1000, "unit": "credits",
          "state": "available", "exhausted_until": null,
          "sources": ["workbuddy","zcode"] },
        { "id":"glm-4.5-air", "display":"GLM-4.5-Air",
          "free": true, "remaining": null, "total": null,
          "state": "available", "sources": ["zcode"] }

```

**这个端点同时服务总面板与 dsh 插件**——一份数据两个消费者，避免两套逻辑漂移。字段直接对应 §8 的可用性矩阵。

### 免费模型：判定与展示

**判定（三级，从严到宽）**

| 级 | 依据 | 可信度 |
|---|---|---|
| 1 | **上游明确标记**：额度接口返回 `unlimited: true` 或单价为 0 | 最高 |
| 2 | **Mergence 倍率表**：该模型在所有来源上的 `ModelRate` 均为 0，或 `costTier == 0`（免费档） | 高 |
| 3 | 不可判定 → **不猜**，显示「—」并归入「未知」 | — |

> **第 3 级刻意保守**：误判免费会让用户以为可以随便用、实际产生费用，**比显示「未知」的代价大得多**。

**展示规则**

| 情况 | 显示 |
|---|---|
| **免费** | 绿色 **「免费」** 徽章，**不显示任何数字**（按用户要求） |
| 有额度 | `820 / 1000`（剩余/总量），剩余 <20% 转黄 |
| **不限量**（非免费，如包月不限量） | **「不限量」** 徽章 |
| 耗尽 | 灰色 **「已耗尽 · 04:00 恢复」**；无恢复时间则只显示「已耗尽」 |
| 未知 | **「—」** |
| 全局不可用 | 整行置灰 + 警示图标 |

> **为什么必须把「免费」和「不限量」分开**：两者对用户的意义完全不同——前者是「不花钱」，后者是「花了钱但随便用」。混在一起会让用户误判成本，这是额度类 UI 最常见的坑。

### 分组与排序

与总面板 §2「列表二」**共用同一套分组逻辑**（按厂商归类，以**上游真实模型**为准，别名在行内标注），保证插件与总面板看到的是**同一个世界**。

### 交互
- 默认按厂商折叠，记住展开状态
- 点击模型 → 展开该模型的各来源渠道明细（对应总面板的抽屉）
- 30 秒自动刷新，支持手动刷新
- Mergence 未运行时显示明确的「**未连接**」，而不是空白或 0

### 实现顺序：排在最后（P9）

三个理由：
1. **完全依赖** Mergence 的两个产出——`/api/quota` 端点与端口发现机制。主体没完成，插件无从对接。
2. 它是**可独立开发的纯前端 + 轻适配**工作，不阻塞主体任何阶段。
3. 主体完成后，`/api/quota` 的数据结构已经过总面板**实战验证**，插件照抄即可，**返工风险最低**。

## 11. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| `new-api` Admin API 未定型（仍发 rc） | P3 返工 | 加适配层隔离，锁定已验证版本 |
| WorkBuddy 搬迁量（约 130 个 Go 文件） | P4 周期长 | 保持旧进程可独立运行，分模块搬、每步可回滚 |
| 反向 2api 项目多声明「仅供学习」 | 合规 | README 明确免责；不随包分发；不承诺商用 |
| 「一键下载」可能被视为协助分发 | License | 改为显式用户触发 + 展示来源与 SHA256 |
| 托管型 provider 硬编码端口 | 动态端口失效 | 降级为「固定端口 + 冲突预检」，冲突时明确报错 |
| 厂商归类的边界模糊（别名映射跨厂商） | 列表二分组不准 | 以**上游真实模型**为归类依据，别名在模型行内以副标题标注 |
| Explorer 重启导致托盘图标消失 | 用户以为程序挂了 | 监听 `TaskbarCreated` 消息并重建图标（P1 必做项） |
| 窗口子类化与 go-webview2 内部过程冲突 | 窗口行为异常 | 只拦 `WM_CLOSE`，**其余一律 `CallWindowProcW` 转发**，不重复实现任何默认行为 |
| 退出时序漏步导致残留 | 幽灵托盘图标 / 孤儿进程占端口 | P1 验收标准写成「进程+子进程全消失、端口全释放、通知区无残留」，逐条可验 |
| 单实例互斥体持有者崩溃 | 后续启动被拒 | 互斥体只管「已存在则唤出」，**不做拒绝启动**；唤出失败则正常新建 |
| 额度查询接口自身故障 | **所有模型被误 ban，服务不可用** | 连续失败 `ban_failure_threshold` 次后转「未知」而**非**「耗尽」；绝不因查询失败而 ban |
| 主动轮询打上游过频被限流 | 影响正常调用 | 被动优先；查询错峰；结果带 TTL 缓存 |
| 免费模型误判 | 用户以为可随便用，实际产生费用 | 三级判定从严；不可判定一律显示「—」，**绝不默认免费** |
| dsh 插件与 dsh 版本耦合（Cordis 插件 API 可能变） | P9 需适配 | 插件只依赖 Mergence 的稳定 HTTP 端点，对 dsh 侧只做薄适配；锁 dsh 版本 |
